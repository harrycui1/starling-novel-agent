# Starling 网文续写 Agent 技术文档（开发交接版）

> 历史记录：这是原流程的设计／验收，不代表全文精简版的当前行为。当前实现见 [全文精简流程](全文精简流程.md)。

> 读者：接手开发的工程师或编码模型。
> 目标：读完这份文档就能开工。文档讲清楚三件事：做什么、按什么结构做、每一步的代码和 Prompt 怎么写。
> 需求来源：飞书文档《【梳理】网文策略规划和问题》（https://bytedance.larkoffice.com/docx/SlYedTySXonzy3xMoRUc20NRnOd ），以及其中引用的《网文续写节点 prompt 参考汇总》。
> 本文所有"默认值"都是为了让开发不被卡住而先定的，可以改，改的时候只改配置，不改代码结构。

## 0. 给接班模型的工作约定

1. **先读后写**。动手前读完本文第 1–6 节。用到 NovelForge 时，先读第 9 节列出的源文件，不要凭印象复刻。
2. **严格按流水线做**。本系统是"固定节点 + 人工卡点"的流水线，不是自主规划的 Agent。不要引入让模型自己决定下一步做什么的循环。
3. **结构化优先**。除正文以外，每个节点的输出都必须是经过 Pydantic 校验的 JSON。校验失败就修复或重试，不允许把未校验的文本传给下一个节点。
4. **不要编造**。遇到不确定的接口、模型名、内部服务地址，在代码里写成配置项并加 `TODO(confirm)` 注释，不要猜一个值硬编码进去。
5. **改动要小**。一次只做一个节点或一个模块，做完写测试、跑通，再做下一个。
6. **每完成一个里程碑（见第 11 节）**，更新本文末尾的"实现进度"表。

## 1. 要做的东西

### 1.1 一句话

编辑上传一篇约 1 万字的网文开头，系统理解原文并生成几个续写方向。编辑选定方向后，系统生成大纲和章节细纲，再批量写出约 2 万字的续写正文，最后交编辑检查提交。

### 1.2 业务流程（来自需求文档泳道图）

```
编辑                                   Starling 网文 Agent
────                                   ───────────────────
上传正文 ─────────────────────────────▶ 提取大纲（理解原文）
                                         │
                                         ▼
收到 3 个剧情走向 ◀──────────────────── 生成灵感：3 个剧情方向
  │
  ▼
选其中一个 / 手动输入 / 自动 ─ ─ ─ ─ ─ ▶ 选择最合适的方向（仅"自动"时）
                                         │
                                         ▼
确认大纲并保存 ◀─────────────────────── 生成大纲（按字数算出章节数）
  │
  └────────────────────────────────────▶ 生成章节细纲
                                         │
                                         ▼
检查、确认、提交 ◀───────────────────── 批量生成正文
```

### 1.3 三个设计约束（所有设计决策都要能回到这三条）

| 约束 | 含义 | 本系统的对应机制 |
|---|---|---|
| 前后一致 | 人设、设定、伏笔不能出错 | 故事状态档案（StoryBible）+ 一致性规则检查 |
| 爽点节奏 | 续写 2 万字符合商业爽点 | 大纲阶段做节奏编排 + 章节审核 |
| 批量稳定且有差异 | 每篇不翻车，篇与篇不雷同 | 自动审核和重写 + 方向去同质化 |

### 1.4 范围

**本期做**：上面流程的全部节点、编辑工作台、任务管理、编辑操作日志、离线评测脚本。

**本期不做，但数据结构要预留**：
- 一稿多产：同一开头、多个方向，各自生成一个版本。本期数据模型要支持"一个开头挂多个版本"，但前端只需要能对一个版本跑完全流程。
- AI 全自动选方向上线：本期只实现"自动"按钮和评审打分逻辑，重点是把编辑的选择记录下来。
- 转短剧：本期不做，StoryBible 和大纲的格式不要写死成只给小说用。
- 作品上线后的数据回流：只预留表字段。

### 2.1 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 后端语言 | Python 3.11+ | 与 NovelForge 一致，Prompt 和解析代码可以直接搬 |
| Web 框架 | FastAPI | 同上 |
| ORM | SQLModel + Alembic | 同上；表结构变更必须走 Alembic 迁移 |
| 数据库 | 开发用 SQLite，上线用 MySQL 或 PostgreSQL | 用 SQLModel 屏蔽差异，不要写方言 SQL |
| 后台任务 | 先用进程内 asyncio 任务 + 数据库状态；需要多机时换成 Celery、RQ 或公司内部队列 | 节点函数要写成可重入，这样换队列时不用改节点代码 |
| LLM 调用 | 自己封装一层 LLM 网关（`llm/gateway.py`），底层可以用 `langchain-openai` 或直接调 HTTP | 模型名和 endpoint 全部走配置，`TODO(confirm)` 公司内可用模型 |
| JSON 修复 | `json_repair` | 和 NovelForge 一致 |
| 前端 | React + TypeScript，组件库沿用 Starling 现有前端 | `TODO(confirm)`：是否并入 `starling_translate_fe` 或 `agent-fe-starling-*`，还是单独建项目 |
| 部署位置 | `TODO(confirm)`：独立服务，或挂到 `agent-starling-pythonllm` | 先按独立服务开发，对外只暴露 HTTP，以后迁移成本低 |

**不用的东西及原因**：
- **Neo4j 知识图谱**：3 万字体量下，一份结构化 JSON 档案就够用，图数据库带来的运维成本收不回来。
- **Electron**：本系统是多编辑协作的平台，不是单机写作工具。
- **向量检索 / RAG**：原文 1 万字、续写 2 万字，都能直接放进长上下文模型。前文太长时用"章节摘要 + 最近一章原文"处理（见 6.6）。

## 4. 数据模型

### 4.1 核心实体关系

```
Project（一份上传的原文）
  ├── SourceText（原文，按章切分）
  ├── StoryBible v0（N1 产出，理解原文后的初始档案）
  ├── DirectionCandidate × N（N2 产出的候选方向）
  └── Version × M（一个选定方向 = 一个续写版本；一稿多产就是多个 Version）
        ├── chosen_direction（选中或编辑过的方向）
        ├── Outline（可多版本，记录编辑修改）
        ├── ChapterPlan × K
        ├── Chapter × K（正文，每章可有多个修订稿）
        │     └── ChapterReview × n
        └── StoryBible vK（每写完一章更新一次，保留每一版快照）
EditorAction（编辑的所有操作，用于沉淀数据）
LLMCall（每次模型调用的记录：节点、模型、token、耗时、prompt 版本）
```

### 4.2 表（SQLModel，字段只列关键的）

```python
class Project(SQLModel, table=True):
    id: int
    title: str
    genre_tags: list[str]          # JSON 列，题材标签，编辑上传时填，N1 可补充
    channel: str                   # 投放渠道，决定字数等规格（见 config）
    source_word_count: int
    created_by: str
    created_at: datetime

class SourceChapter(SQLModel, table=True):
    id: int
    project_id: int
    index: int                     # 从 1 开始
    title: str
    content: str

class StoryBibleSnapshot(SQLModel, table=True):
    id: int
    project_id: int
    version_id: int | None         # None = 原文理解阶段的 v0
    after_chapter: int             # 写到第几章后的状态；v0 为原文最后一章序号
    data: dict                     # JSON，结构见 4.3 StoryBible
    created_at: datetime

class DirectionCandidate(SQLModel, table=True):
    id: int
    project_id: int
    batch_id: str                  # 同一次生成为一批
    data: dict                     # 结构见 schemas/direction.py
    judge_scores: dict | None      # N3 评审打分
    shortlisted: bool              # 是否进入最终给编辑看的 3 个

class Version(SQLModel, table=True):
    id: int
    project_id: int
    direction_source: str          # "candidate" | "edited" | "manual" | "auto"
    direction_candidate_id: int | None
    direction: dict                # 最终生效的方向卡（编辑改过的以这里为准）
    target_words: int              # 续写目标字数，默认 20000
    status: str                    # 状态机，见第 5 节
    current_node: str
    error: str | None

class OutlineRevision(SQLModel, table=True):
    id: int
    version_id: int
    rev: int
    data: dict                     # 结构见 schemas/outline.py
    author: str                    # "ai" 或编辑 ID
    confirmed: bool

class ChapterPlanRow(SQLModel, table=True):
    id: int
    version_id: int
    index: int                     # 续写章节号，接在原文最后一章后面
    data: dict

class ChapterDraft(SQLModel, table=True):
    id: int
    version_id: int
    index: int
    rev: int                       # 0 = 首稿，之后是自动重写或编辑修改
    title: str
    content: str
    word_count: int
    author: str                    # "ai" 或编辑 ID
    is_current: bool

class ChapterReview(SQLModel, table=True):
    id: int
    draft_id: int
    verdict: str                   # "pass" | "revise" | "block"
    rule_issues: list[dict]        # 规则检查器发现的问题
    llm_review: dict               # 模型审核结果（结构见 schemas/review.py）

class EditorAction(SQLModel, table=True):
    id: int
    project_id: int
    version_id: int | None
    editor: str
    action: str                    # 见下方枚举
    payload: dict                  # 操作前后内容、原因
    created_at: datetime

class LLMCall(SQLModel, table=True):
    id: int
    version_id: int | None
    node: str
    prompt_name: str
    prompt_version: str            # 模板文件头里的版本号
    model: str
    input_tokens: int
    output_tokens: int
    latency_ms: int
    success: bool
    raw_output_path: str | None    # 原始输出落盘位置，方便排查
```

`EditorAction.action` 枚举（这批数据就是"编辑经验沉淀"，一个都不能漏记）：
`upload`、`direction_select`、`direction_edit`、`direction_manual`、`direction_auto`、`direction_reject`、`direction_regenerate`、`outline_edit`、`outline_confirm`、`chapter_edit`、`chapter_regenerate`、`version_submit`、`version_abandon`。
其中 `direction_select` 的 payload 必须带上：当时展示的 3 个候选 ID、选中的 ID，以及编辑可选填的理由。

### 4.3 StoryBible（故事状态档案，系统核心）

所有节点都读它，N6 每写完一章更新一次。它解决"前后一致"的问题：模型写第 8 章时，不靠回忆两万字前文，而是拿到一份明确的事实清单。

```python
class Evidence(BaseModel):
    chapter: int                   # 原文或续写的章节号
    quote: str                     # ≤ 40 字的原文引用

class Character(BaseModel):
    name: str
    aliases: list[str]             # 别名、外号
    role: Literal["protagonist", "deuteragonist", "antagonist", "supporting", "minor"]
    personality: list[str]         # 3–5 个关键词
    speech_style: str              # 说话口吻，一两句话
    goal_now: str                  # 当前目标（随剧情更新）
    status_now: dict[str, str]     # 可变状态：等级/修为/身份/资产/伤势等，key 由题材决定
    addressing: dict[str, str]     # 对其他角色的称谓，例如 {"林婉": "婉儿"}
    evidence: list[Evidence]

class Relation(BaseModel):
    a: str
    b: str
    kind: str                      # 同盟/敌对/亲属/师徒/恋人/上下级/其他……
    stance_a_to_b: Literal["友好", "中立", "敌意", "未知"]
    note: str
    evidence: list[Evidence]

class WorldRule(BaseModel):
    rule: str                      # 只记原文明确写过的规则
    evidence: list[Evidence]

class TimelineEvent(BaseModel):
    chapter: int
    event: str                     # 单句，可独立理解

class Foreshadow(BaseModel):
    id: str                        # F1, F2 ...
    content: str
    planted_in: int
    status: Literal["open", "paid_off", "dropped"]
    paid_off_in: int | None
    plan_note: str | None          # 大纲阶段写入：打算在哪一章、怎么回收

class StyleProfile(BaseModel):
    pov: Literal["第一人称", "第三人称限知", "第三人称全知", "多视角"]
    tense_and_voice: str           # 叙述习惯描述
    dialogue_ratio: float          # 原文对话占比，规则检查器计算，不让模型估
    avg_sentence_len: float        # 规则检查器计算
    avg_paragraph_len: float       # 规则检查器计算
    tone: list[str]                # 爽、虐、轻松、悬疑……
    sample_passages: list[str]     # 3 段代表性原文，每段 200–400 字，写正文时作为风格样例

class StoryBible(BaseModel):
    genre_tags: list[str]
    selling_points: list[str]      # 原文卖点
    logline: str                   # 一句话梗概
    characters: list[Character]
    relations: list[Relation]
    world_rules: list[WorldRule]
    timeline: list[TimelineEvent]
    foreshadows: list[Foreshadow]
    style: StyleProfile
    chapter_digests: list[dict]    # [{chapter, title, digest(300–500字)}]，原文和续写章节都在这里
```

**硬规则**：
- 角色名单是封闭集合。续写正文里出现名单之外的有名角色，属于一致性问题（见 6.5 规则检查）。确实需要新角色时，必须在大纲或细纲阶段显式加入 `new_characters`，编辑确认后写进档案。无名龙套（"店小二""守卫"）不受限，但不得超过 2 个，不得有背景故事。
- `status_now`、`goal_now`、`addressing`、伏笔状态只能由 N6 的档案更新步骤修改，其他节点只读。
- 文风统计数字（对话占比、平均句长、平均段长）由代码计算，不让模型估。

## 5. 流水线与状态机

### 5.1 状态

`Version.status` 取以下值：

```
created
  → understanding            # N1（项目级，只在第一个版本前跑一次；多版本共用 StoryBible v0）
  → generating_directions    # N2（项目级）
  → awaiting_direction       # 编辑卡点 1
  → judging                  # 仅编辑点了"自动"时进入 N3
  → generating_outline       # N4
  → awaiting_outline         # 编辑卡点 2
  → planning_chapters        # N5
  → writing                  # N6，带子进度 current_chapter / total_chapters
  → awaiting_review          # 编辑卡点 3
  → submitted
任意状态 → failed（记录 error 和失败节点）
任意状态 → abandoned
```

注意：N1 和 N2 的产物挂在 Project 上，不属于某个 Version。实现时可以把 Project 也做成一个小状态机，或者让第一个 Version 驱动 N1、N2。推荐前者，这样一稿多产时直接复用。

### 5.2 Runner 的写法要求

- 每个节点是一个 `async def run(ctx: NodeContext) -> NodeResult` 函数，**可重入**：用同样的输入重跑，结果覆盖上一次（产物以新版本号写入，不删旧版本）。
- Runner 只负责：读状态 → 调用对应节点 → 写产物 → 推进状态 → 推送 SSE 事件。业务逻辑不要写在 Runner 里。
- 编辑卡点就是"状态停在 `awaiting_*`，等 API 调用后再继续"，不要用轮询或阻塞等待。
- 失败处理：节点内部的模型调用自带重试（见 7.4）。节点整体失败时进入 `failed`，前端提供"从该节点重跑"按钮，对应 API `POST /versions/{id}/retry`。
- N6 断点续写：已经通过的章节不重写，从第一个没有 `pass` 的章节继续。
- 并发：同一个 Version 内章节严格串行；不同 Version 之间并行，并发数走配置 `MAX_PARALLEL_VERSIONS`。

## 6. 节点详细设计

每个节点按"输入 / 输出 / 步骤 / 校验 / Prompt 要点"来写。Prompt 模板正文放在 `app/prompts/`，写法见第 7 节。

### 6.1 N1 理解原文 → StoryBible v0

**输入**：`SourceChapter` 列表、编辑填的题材标签。
**输出**：`StoryBibleSnapshot(after_chapter=原文最后一章)`。

**步骤**：
1. **切章**：用户上传的是整段文本时，按"第X章"等标题的正则切分。切不出章节时，按约 2500 字一段、在段落边界切开，作为伪章节。
2. **代码计算文风统计**：对话占比（引号内字数 / 总字数）、平均句长、平均段长。
3. **逐章摘要**（可并行）：Prompt 参考 NovelForge `拆书_章节大纲摘要.txt`，每章 300–500 字，聚焦关键冲突、行动、转折、信息揭示、章末悬念。
4. **全文抽取 StoryBible**：一次调用。输入原文全文 + 各章摘要，按 StoryBible 的 Schema 输出（`style` 里的统计字段由代码填，不让模型填）。原文 1 万字，放进长上下文模型没有问题。
5. **伏笔补抽**：单独调用一次，只抽"已埋下、尚未回收"的伏笔，避免第 4 步抽漏。
6. **证据核对（代码）**：每条 `evidence.quote` 必须能在原文中找到（允许去掉标点、空白后再匹配）。找不到的条目标记为 `unverified`，在前端展示，不直接删除。
7. **选风格样例（代码 + 模型）**：从原文挑 3 段，分别覆盖对话密集段、动作段、心理或描写段，写入 `style.sample_passages`。

**校验**：Schema 校验通过；主角至少 1 个；每个角色至少有 1 条通过核对的证据。

### 6.2 N2 生成剧情方向

**输入**：StoryBible v0、渠道规格、近期同质化参考（见下）。
**输出**：一批 `DirectionCandidate`，其中 3 个 `shortlisted=True`。

**方向卡 Schema**（`schemas/direction.py`）：

```python
class Direction(BaseModel):
    title: str                     # 4–12 字，有辨识度
    hook: str                      # 一句话卖点
    core_conflict: str             # "A 与 B 因为 C 而冲突"
    main_trope: str                # 主套路，取自配置里的套路词表（打脸/逆袭/掉马/追妻/复仇/揭秘/升级……）
    secondary_tropes: list[str]
    payoff_plan: list[str]         # 3–5 个关键爽点，按顺序
    ending: str                    # 结局落点（短篇要收束）
    uses_foreshadows: list[str]    # 打算回收的伏笔 ID
    new_characters: list[dict]     # 需要新增的角色（名字、作用），可以为空
    differentiation: str           # 和另外几个方向的区别
    synopsis: str                  # 300–600 字的方向梗概
```

**步骤**：
1. **发散**：一次生成 `N2_CANDIDATES`（默认 8）个方向。Prompt 要求主套路尽量互不相同，并且只能基于 StoryBible 已有的人物和设定展开。
2. **去重（代码）**：两两计算梗概的相似度（embedding 余弦相似度，或简单的字符 n-gram Jaccard，先用后者，不依赖外部服务）。主套路相同且相似度超过 `N2_DEDUP_THRESHOLD` 的，只保留一个。
3. **平台级去同质化（代码）**：查询近 `N2_RECENT_WINDOW_DAYS` 天同题材 Version 选中方向的 `main_trope` 分布，占比过高的套路降权。表里数据为空时跳过这一步。
4. **评审打分**：调用 N3 的评审 Prompt，给每个候选打分（维度见 6.3）。
5. **选出 3 个（代码）**：按分数排序，贪心选取，约束是 3 个方向的 `main_trope` 两两不同。
6. **编辑点"换一批"时**：把上一批的标题和主套路作为"避免重复"的输入，再跑一次 N2。

**校验**：`uses_foreshadows` 里的 ID 必须存在于 StoryBible；`new_characters` 不能和已有角色重名。

### 6.3 N3 选择方向

**编辑卡点 1**，编辑有四种操作：
- **选一个**：`direction_source=candidate`。
- **选一个并修改**：`direction_source=edited`，修改前后都要记进 `EditorAction`。
- **手动输入**：`direction_source=manual`。编辑写的是自由文本，系统先调用一次"方向规范化"Prompt，把它整理成 `Direction` 结构，再给编辑确认。
- **自动**：`direction_source=auto`，取 N2 打分最高的那个。只有编辑选了"重新评审"时才重新打分。

**评审 Prompt**（`n3_judge.md`）的打分维度，每项 1–5 分，并要求先给理由再给分：
- `consistency`：是否和 StoryBible 冲突（人设、规则、已发生事件）
- `payoff_strength`：爽点强度和兑现密度
- `capacity`：能否撑满目标字数，不会太单薄也不会太满
- `novelty`：是否跳出常见套路
- `channel_fit`：是否符合渠道和题材的读者预期

总分 = 加权和，权重走配置。打分结果写入 `DirectionCandidate.judge_scores`，评审理由要完整保存，以后用来和编辑的真实选择对比，校准评审模型。

### 6.4 N4 生成大纲

**输入**：StoryBible、Version.direction、目标字数、渠道规格。
**输出**：`OutlineRevision(rev=1, author="ai")`。

**章节数计算（代码，不让模型算）**：
```
chapter_words = config.channels[channel].chapter_words      # 默认 2500
n_chapters = round(target_words / chapter_words)            # 2 万字 → 8 章
n_chapters = clamp(n_chapters, MIN_CHAPTERS, MAX_CHAPTERS)
```
把 `n_chapters` 作为硬性参数传给 Prompt，并校验输出的章数和它相等。

**大纲 Schema**：

```python
class OutlineChapter(BaseModel):
    index: int                     # 续写章节号，原文最后一章 +1 开始，连续
    title: str
    function: Literal["铺垫", "冲突升级", "爽点兑现", "反转", "高潮", "收束"]
    summary: str                   # 150–300 字
    payoff: str | None             # 本章兑现的爽点（没有就写 None）
    hook: str                      # 章末钩子
    foreshadow_ops: list[dict]     # [{"id": "F1", "op": "payoff" | "plant", "note": ...}]

class Outline(BaseModel):
    arc_summary: str               # 整体走向，300–500 字
    chapters: list[OutlineChapter]
    new_characters: list[dict]     # 沿用方向卡里的，或在这里新增
```

**节奏规则（代码校验，参数走配置，默认值见第 10 节）**：
- 第 1 章不能是纯"铺垫"，必须承接原文结尾，推进冲突。
- 相邻两个 `payoff` 非空的章节之间，最多隔 `MAX_GAP_BETWEEN_PAYOFFS` 章（默认 2）。
- 最后一章 `function` 必须是"收束"，或者是"高潮"且 `summary` 里写清了结局。
- 方向卡 `uses_foreshadows` 里的伏笔，必须在某一章的 `foreshadow_ops` 里被 `payoff`。
- 每章 `hook` 不能为空（最后一章除外）。

校验不通过时，把具体违反了哪条规则拼进 Prompt，让模型修正，最多 2 次；还不通过就标记给编辑，不阻塞流程。

**编辑卡点 2**：编辑可以直接改大纲（每次保存生成一个新的 `rev`），确认后进入 N5。编辑确认后的大纲里如果有 `new_characters`，要合并进当前的 StoryBible，并生成一个新快照。

### 6.5 N5 生成章节细纲

**输入**：StoryBible、已确认的大纲。
**输出**：每章一条 `ChapterPlanRow`。

```python
class Scene(BaseModel):
    location: str                  # 只能用 StoryBible 里出现过的地点，或者中性描述（"城中""屋内"）
    characters: list[str]          # 只能从 StoryBible 角色名单里选
    beats: list[str]               # 3–6 个情节节拍，按顺序
    purpose: str                   # 这个场景在本章的作用

class ChapterPlan(BaseModel):
    index: int
    title: str
    pov_character: str             # 视角人物
    scenes: list[Scene]            # 2–4 个
    payoff_detail: str | None      # 爽点具体怎么写
    foreshadow_ops: list[dict]     # 继承大纲，可以细化
    ending_beat: str               # 章末停在哪个具体瞬间
    target_words: int
```

**步骤**：一次调用生成全部章节的细纲（保证前后连贯）。章节多于 10 章时，按每 5 章一批分批生成，每批都带上前面已生成的细纲。

**规则检查（代码，`checks/plan_coverage.py`）**：
- 章节号和大纲一一对应；
- `characters`、`pov_character` 都在角色名单里；
- 大纲里每个 `foreshadow_ops` 在细纲里都有对应；
- 所有章节的 `target_words` 加起来，和目标字数的偏差在 ±10% 以内。

### 6.6 N6 批量写正文 + 自动审核

这是最复杂、调用量最大的节点，按章循环：

```
for chapter in plans (按 index 顺序):
    ctx = build_write_context(chapter)          # 见下方"上下文组装"
    draft = write_chapter(ctx)                  # 写作模型
    for attempt in range(MAX_REWRITE + 1):
        rule_issues = run_rule_checks(draft)    # 代码检查
        review = llm_review(draft, ctx)         # 审核模型
        verdict = merge_verdict(rule_issues, review)
        save(draft, review)
        if verdict == "pass": break
        if attempt == MAX_REWRITE or verdict == "block": mark_for_editor(); break
        draft = rewrite_chapter(draft, rule_issues, review, ctx)
    update_story_bible(draft)                   # 无论是否 pass，都要更新档案，后面的章节才能接得上
    push_progress()
```

**上下文组装（`pipeline/context.py`，写作质量的关键）**

每章的写作 Prompt 按以下顺序拼接，越靠后的内容对模型越重要：
1. 角色和总体写作规范（固定）
2. StoryBible 精简版：只放本章出场角色的完整卡片，其他角色只放名字和一句话身份；世界规则全放；伏笔只放本章要操作的和仍处于 `open` 状态的
3. 文风画像 + 3 段风格样例原文
4. 全书梗概：方向卡 synopsis + 大纲 arc_summary
5. 前情：`chapter_digests` 中除最近一章外的所有摘要（原文和已续写章节都算）
6. 上一章正文的完整内容。第 1 章续写时，就是原文最后一章，这一条最影响衔接是否自然
7. 本章细纲（ChapterPlan 全文）
8. 本章硬性要求：目标字数、结尾要求、禁用表达清单

上下文总长度超过 `CONTEXT_BUDGET_TOKENS` 时，按以下顺序裁剪：先把前情摘要压缩成每章 100 字 → 风格样例减到 1 段 → 非出场角色只保留名字。第 6、7、8 项永远不裁。

**写作 Prompt 要点**（`n6_write_chapter.md`），融合参考汇总里"灵犀速写一次一章"、社区热门提示词和 NovelForge"内容生成"三份模板：
- 从上一章最后的动作、场景、情绪或对话直接接着写，不复述前文。
- 用视角人物的限知视角，不透露视角人物不可能知道的信息。
- 只写细纲范围内的剧情，不推进到后续章节；不新增有名角色；不扩展档案以外的设定细节（例如档案只写了"万法阁在青云城"，就不要写成"青云城西街万法阁"）。
- 对话占比贴近原文统计值（±10 个百分点），每句重要对话都要推动剧情、制造冲突或暴露人物。
- 结尾停在一个正在发生的具体瞬间，禁止总结句和预告句。
- 只输出"第X章 标题"和正文，不输出任何分析或说明。
- 模型支持 thinking 时，Prompt 里那些"写前内部分析""写后自检"的步骤，交给 thinking 去做，正文只要结果。

**规则检查（`checks/`，纯代码，结果是确定的）**：

| 检查项 | 判定 | 级别 |
|---|---|---|
| 字数 | 偏离目标超过 ±20% | revise |
| 禁用结尾 | 最后 3 段命中禁用句式词表（"这一切才刚刚开始""命运的齿轮"等，词表放配置文件） | revise |
| 禁用高频词 | 命中次数超过阈值（"一丝""不容置疑""他知道"……） | revise |
| 陌生角色 | 出现疑似人名，但不在角色名单和别名里（用分词或 NER 加白名单）。只统计出现 2 次及以上的 | revise；名字是主要角色的近似写错时为 block |
| 称谓 | 对话里 A 对 B 的称谓和 `addressing` 不一致 | revise |
| 章节标题 | 格式不是"第X章 ……"或章号不连续 | 自动修正，不判为问题 |
| 输出污染 | 正文里出现"以下是""本章""字数统计"等元信息 | 自动删除后复查 |

**模型审核（`n6_review_chapter.md`）**：参考 NovelForge `章节审核.txt` 的维度，但**改成 JSON 输出**，方便程序处理：

```python
class ChapterReviewResult(BaseModel):
    verdict: Literal["pass", "revise", "block"]
    consistency_issues: list[Issue]    # 人设、设定、时间线冲突，必须引用原文（≤20字）+ 档案条目
    plan_deviation: list[Issue]        # 偏离细纲：漏写节拍、越界写到后面的剧情
    pacing_issues: list[Issue]
    ai_flavor_issues: list[Issue]      # 套话、重复句式、空泛情绪
    hook_ok: bool
    payoff_ok: bool                    # 细纲要求的爽点是否兑现
    fix_suggestions: list[str]         # 可执行的修改建议，给重写步骤用

class Issue(BaseModel):
    severity: Literal["low", "mid", "high"]
    quote: str
    reason: str
```

`merge_verdict` 的合并规则：规则检查或模型审核任一方给出 block → block；任一方给出 revise → revise；否则 pass。审核模型和写作模型尽量用不同的模型，避免"自己审自己"。

**重写（`n6_rewrite_chapter.md`）**：输入原稿 + 问题清单 + 修改建议 + 原上下文，要求只改有问题的部分，保留其余内容。重写稿作为新的 `rev` 保存，前端可以看前后对比。

**档案更新（`n6_bible_update.md`）**：参考 NovelForge 的"角色动态信息提取"和"关系提取"，输出**增量补丁**，不重新输出整份档案：

```python
class BiblePatch(BaseModel):
    chapter_digest: str                       # 本章摘要 300–500 字
    timeline_add: list[TimelineEvent]
    character_updates: list[dict]             # {name, goal_now?, status_now?{}, addressing?{}}
    relation_updates: list[Relation]
    foreshadow_updates: list[dict]            # {id, status, paid_off_in} 或新增伏笔
```

由代码把补丁合并进上一版档案，生成新快照。合并规则：只允许更新已有角色；补丁里出现名单外的角色名时，丢弃这一条并记录警告。

**编辑卡点 3**：编辑可以逐章查看正文、审核意见、修改历史；可以直接修改某一章，或者让某一章带着编辑的意见重写。重写某一章之后，后面的章节标记为"可能不连贯"，由编辑决定是否连带重写后续章节，系统不自动级联重写。最后提交。

## 7. Prompt 编写规范

### 7.1 文件格式

每个模板是一个 Markdown 文件，文件头写元信息：

```markdown
---
name: n6_write_chapter
version: 2026-10-27.1
model_role: writer          # 对应 config 里的模型路由：writer / reviewer / extractor / judge
output: text                # text 或 json
schema: null                # output=json 时写 Pydantic 类的路径，例如 app.schemas.review.ChapterReviewResult
---

# 角色
...

# 输入
{{ story_bible_brief }}
...
```

- 模板引擎用 Jinja2，变量名用 snake_case。
- 修改模板必须同时修改 `version`。每次模型调用都要把 `prompt_version` 写进 `LLMCall`，这样评测结果才能对应到具体的 Prompt 版本。
- Prompt 里不写死字数、章数、阈值，统一从变量注入。

### 7.2 内容写法

1. **结构固定**，依次为：角色 → 任务 → 输入（用清楚的分节标题把各种材料分开）→ 硬约束 → 输出格式。
2. **约束写成可以检查的形式**。例如写"对话占比 30%–45%"，不写"多用对话"；写"结尾最后一段必须是一个具体动作、一句对话或一个感官细节"，不写"结尾要有余味"。
3. **禁止项给例子**。参考汇总里的写法，比如"不得补充未提供的方位信息：档案写'万法阁位于青云城'，就不能写'青云城西街'"，这比一句抽象规则有效得多。
4. **把输入材料放在指令前面，最关键的要求放在最后**。长上下文里，模型对开头和结尾的内容更敏感。
5. **正文类 Prompt 不要求模型输出分析过程**，需要推理时交给 thinking。
6. **JSON 类 Prompt** 由 `llm/structured.py` 自动把 Schema 附在末尾，模板里不要手写 Schema。

### 7.3 从参考汇总迁移时要注意

参考汇总里的 NovelForge 模板依赖它自己的运行时：`@KB{...}` 知识库引用、"指令流"输出协议（`{"op":"done"}`）、`/nothink`、`【事实子图】`。迁移时：
- `@KB{ name=文风约束 }` → 换成 StoryBible 的 `style` 和样例段落；
- "指令流"输出协议 → 去掉，统一改成"输出符合 Schema 的 JSON"；
- `【事实子图】`、`【引用上下文】` → 换成第 6.6 节的上下文组装结果；
- `/nothink` → 去掉，由 LLM 网关根据模型和节点配置决定是否开启 thinking。

### 7.4 结构化输出的处理流程（`llm/structured.py`）

```
调用模型
  → 提取 JSON（去掉 ```json 代码块包裹，截取第一个 { 到最后一个 }）
  → json.loads 失败时，用 json_repair 修复
  → Pydantic 校验
  → 校验失败：把错误信息拼进追加消息，让模型修正，最多 STRUCTURED_MAX_RETRY（默认 2）次
  → 仍然失败：抛出 StructuredOutputError，由节点决定进入 failed 状态还是降级处理
```
每次原始输出都要落盘（`raw_output_path`），排查问题时用。

## 8. API

所有接口返回 JSON。长任务立即返回，进度通过 SSE 推送。

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/projects` | 上传原文（文本或 txt/docx 文件）+ 题材标签 + 渠道，触发 N1、N2 |
| GET | `/projects/{id}` | 项目详情：原文章节、StoryBible v0、候选方向 |
| POST | `/projects/{id}/directions/regenerate` | 换一批方向 |

## 12. 测试和评测

### 12.1 测试

- **单元测试**：所有 Schema、规则检查器、章节数计算、节奏规则、补丁合并、上下文裁剪。规则检查器每条规则都要有"命中"和"不命中"两类用例。
- **流水线测试**：实现 `FakeLLM`，按 `prompt_name` 返回 `tests/fixtures/` 里录制好的响应，跑通 created → submitted 全流程，以及失败重跑、断点续写。CI 里不调用真实模型。
- **真实模型冒烟测试**：标记为 `@pytest.mark.live`，默认不跑，手动触发。

### 12.2 离线评测（`eval/`）

样本：挑一批已完结、表现好的短篇，取前约 1 万字作为输入，原作后续用来对照。`TODO(confirm)` 样本来源和数量，建议先准备 20 篇。

| 指标 | 怎么算 |
|---|---|
| 一致性错误率 | 每万字的 high 级 `consistency_issues` 数，由一个独立的审核模型统计，再人工抽查校准 |
| 规则问题率 | 首稿命中规则检查的章节占比 |
| 首稿通过率 | 首稿 verdict=pass 的章节占比 |
| 平均重写次数 | 每章平均重写几次 |
| 方向差异度 | 同一批 3 个方向两两之间相似度的平均值（越低越好） |
| 批间同质化 | 不同项目选中方向的主套路分布熵、正文 n-gram 重合度 |
| 成本和耗时 | 每万字 token 数和总耗时，从 `LLMCall` 汇总 |

线上指标（预留字段，本期不实现采集）：编辑方向采纳率、编辑修改幅度（修改前后的编辑距离）、上线后的完读率和追读率。
