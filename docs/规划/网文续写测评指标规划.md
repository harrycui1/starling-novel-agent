---
title: 网文续写测评指标规划
---

**一句话结论：编辑定义目标，机评放大目标。** 这一阶段的目标是把续写稿调到"拿得出手"，再上线拿读者数据。编辑负责判断稿子好不好、坏在哪里；机评学习编辑的判断，用来筛稿和快速迭代；机评只有在与编辑校准一致后才能用来下结论。

# 一、背景与目标

## 1.1 要证明的命题

给定一篇约 1 万字、已写完结局的短篇，系统保留前约 60%～80%，从切点续写约 2 万字。要证明的只有一件事：

> 编辑把 AI 续写稿改到能发的成本，低于编辑自己写或外包写的成本。

"流程跑通了""token 下降了"都不回答这个问题，不作为质量结论。

## 1.2 现状

| 项目 | 现状 |
|---|---|
| 质量 | 第一轮编辑盲评（4 本书 × 2 个版本 × 2 位编辑）结论：两个版本都不能用 |
| 根因 | 切点落在主要矛盾解决之后；类型跑偏（爽文写成成长文）；形式偏离原作（单章长 2～4 倍、章尾落在内心独白） |
| 评测方式的问题 | 1～5 分六维打分，编辑之间的分歧大于版本之间的差距；六个维度分数几乎一致，实际只是一个整体判断 |
| 有价值的部分 | 编辑的文字评语，三个根因都是从评语里找到的 |

## 1.3 本文要回答的问题

1. 编辑评测和机评是什么关系。
2. 编辑看什么、怎么看。
3. 机评看什么、怎么校准。
4. 这一阶段做到什么程度算完成。
5. 评测节奏和人力怎么安排。

# 二、评测架构

## 2.1 核心思路：编辑定义目标，机评放大目标

| 角色 | 负责什么 | 特点 |
|---|---|---|
| 读者（上线后） | 最终标准：完读、付费 | 最真实，但要上线才有 |
| 编辑 | 定义什么是好：什么叫爽、什么叫跑偏、什么样的稿子拿得出手 | 准，但贵、慢、人和人有差异 |
| 机评 | 学习编辑的判断，复制到所有稿子上 | 不懂品味，但便宜、快、稳定 |
| 生产流程 | 把可靠的机评指标变成写作约束或同步校验 | 在生成时就把问题挡住 |

整条链是：读者 → 编辑 → 机评 → 生产流程。上一级校准下一级。当前没有读者数据，编辑是最高标准；上线后，编辑判断也接受读者数据校准。

从算法角度看，这是 RLHF 的结构：编辑判断是人类偏好，机评是奖励模型，提示词和工作流是被优化的策略。

## 2.2 两者如何连接：校准循环

1. 编辑评一批稿子，给出判断和原因。
2. 机评对同一批稿子给出判断，计算与编辑的一致率。
3. 一致率达标后，日常大量稿子交给机评，编辑只抽查。
4. 编辑发现机评判不出的新问题，补进机评。

## 2.3 按维度性质分工

| 维度性质 | 例子 | 编辑与机评的关系 |
|---|---|---|
| 可客观计算 | 章长比、对话占比、章尾类型、事实矛盾 | 机评完全承担，不占编辑时间 |
| 有明确锚点的判断 | 类型是否跑偏、被删高光是否兑现、反派下场是否降级 | 先重叠后交接：校准期两边评同一批，可靠后交给机评，编辑定期抽查 |
| 品味 | 爽不爽、想不想往下读 | 编辑始终是标准；机评只做初筛和排序 |

## 2.4 两条纪律

**纪律一：编辑评测是测试集，不是开发集。** 日常可以对着机评反复调提示词，但迭代算不算进步，以没参与调参的编辑评测为准，否则系统学会的只是讨好机评。凡是同时写进提示词作为约束的指标，它的机评分数只说明模型有没有执行，不说明质量。

**纪律二：指标有生命周期。**

编辑发现问题 → 机评量化 → 与编辑校准 → 进入生产流程（提示词约束或同步校验）→ 编辑只做抽查

控制和评测是同一条流水线的不同阶段。章长是走完这一整圈的例子：编辑点名，代码量化，进入生产。每个指标都应标明当前处在哪个阶段。

# 三、北极星指标与阶段退出标准

## 3.1 北极星指标

| 阶段 | 北极星指标 |
|---|---|
| 当前（上线前） | 编辑改到能发的成本，用"可发档位"衡量 |
| 上线后 | 读者完读率、付费转化，与原作对比 |

## 3.2 可发档位

用改稿时间定义，替代 1～5 分的抽象打分：

| 档位 | 含义 |
|---|---|
| A | 直接能发，或只改错字 |
| B | 小改，1 小时内能发 |
| C | 大改，1～4 小时 |
| D | 不如重写 |

时间是具体的，编辑之间更容易一致，而且直接对应核心命题。

## 3.3 阶段退出标准（草案，待定）

评测集 8 本书中，至少一半达到 B 档或以上，且没有 D 档。达到后进入线上小流量测试。

这个标准的松紧决定整套指标的阈值，需要产品和编辑负责人共同确认。

# 四、编辑评测

## 4.1 编辑交出三样东西

| 产出 | 作用 | 第一轮是否有 |
|---|---|---|
| 判断：哪篇更好、能不能发 | 目标本身 | 有，但六维打分噪声大 |
| 原因：为什么输、为什么不能发 | 机评学习的材料 | 有，在文字评语里 |
| 新问题：现有指标都没覆盖的问题 | 指标生命周期的起点 | 有，在文字评语里 |

**当前阶段原因比判断更重要。** 已经知道稿子不好，现在缺的是具体坏在哪里。

## 4.2 评测形式

沿用第一轮的文字评语形式，粒度合适，不重新设计。调整两处：

1. 增加可发档位（A～D），用于判断是否达到退出标准。
2. 迭代比较时用成对比较：同一本书的两个版本放在一起，选一篇，再从固定原因标签里勾一个主要输的原因，可以补充评语。不再做六维 1～5 分。

原因标签（初版，待编辑确认）：类型跑偏、切点不对、第二冲突生硬、不够爽、节奏拖、高光降级、人设崩、文风不像原作或 AI 味重、逻辑错误。

原因标签是编辑和机评之间的桥梁：

- 统计出现最多的标签，就是下一轮要改的地方。
- 每个标签必须对应至少一个机评指标。编辑勾了某个标签而机评没报警，说明机评有漏洞，需要修。

## 4.3 按材料粒度分层，迭代主要在便宜的层上跑

速度的瓶颈不是编辑小时数，而是每次判断要读多少字。

| 评什么 | 编辑读多少 | 单次耗时 | 一天约能做 | 验证什么 |
|---|---|---|---|---|
| 方向/路线 | 约 1500 字梗概和高光账本 | 5 分钟 | 50～80 组 | 切点、类型、第二冲突 |
| 大纲 | 约 3000 字 | 10 分钟 | 30 组 | 节奏结构、高潮位置 |
| 关键片段 | 续写前 3 章或终局 3 章 | 10～15 分钟 | 25 组 | 开头是否抓人、新高是否成立 |
| 全文 | 2 万字 × 2 | 60 分钟以上 | 6 组 | 阶段性确认、可发档位 |

前提需要验证：方向、大纲、片段上的判断能否预测全文判断。在第一次全文评测时顺带检验；如果预测不了，就只能更多依赖全文评测。

## 4.4 人力与防疲劳

人力预算：1～2 位编辑，每周共 1～2 人天。

| 措施 | 目的 |
|---|---|
| 大部分样本两位编辑分开评，约 20% 两人都评 | 吞吐量翻倍，同时持续监测两人一致性 |
| 定期重复几组固定的锚点对比（含明显好、明显跑偏的样本） | 检测编辑标准是否漂移 |
| 混入人写的稿子 | 检验盲评是否有效，避免编辑只是在识别 AI 痕迹 |
| 单次评测不超过 2 小时 | 防止疲劳 |
| 全程盲评，打乱顺序 | 消除对 AI 稿和位置的偏差 |

# 五、机评指标

机评指标从两个来源推导：编辑点名的失败原因，以及产品原则。不照搬外部 benchmark。

## 5.1 送审门槛：不达标不送编辑

| 层 | 指标 | 定义 | 初始阈值 |
|---|---|---|---|
| 方案 | 切点合规 | 切点在"门关上"之前，保留原文 ≥ 60% | 必须满足 |
| 方案 | 高光账本覆盖 | 被删的原作高光在方案里都有去处 | 100% |
| 方案 | 势能强度 | 第二冲突所用势能强度 ≥ 3 | 必须满足 |
| 形式 | 章长比 | 续写章长中位数 ÷ 原文章长中位数 | 0.8～1.3 |
| 形式 | 对话占比差 | 续写与原文对话占比之差 | ≤ 10 个百分点 |
| 形式 | 段落长度比 | 续写段落平均字数 ÷ 原文 | 0.8～1.3 |
| 形式 | 章尾事件率 | 章尾落在事件或对话上的章节占比 | ≥ 80% |
| 形式 | AI 套话密度 | 每千字套话数（中文套话表） | 不超过原文的 2 倍 |
| 形式 | 复述率 | 续写与前文的重复比例 | 待定 |

阈值均为初值，用第一轮已评稿子回测校准：被编辑批评的稿子应落在阈值外，未被批评的应落在阈值内。

## 5.2 诊断指标：不拦稿，解释编辑的结果

| 指标 | 对应原因标签 | 怎么测 |
|---|---|---|
| 类型跑偏违规数 | 类型跑偏 | 评审模型逐条核对类型契约中的禁止走向，目标为 0 |
| 反派下场达标 | 不够爽 | 是非题：是否达到读者期待的程度 |
| 高光兑现率 | 高光降级 | 高光账本中每条在正文里是否兑现，强度不低于原作 |
| 新高胜率 | 不够爽 | 续写终局高光与原作最强高光成对比较 |
| 节奏指标 | 节奏拖 | 爽点或反转的间隔，规则待定（先请编辑在原作上标注爽点位置，归纳后定） |
| 每万字矛盾数 | 逻辑错误 | 独立的全文一致性检查，只统计续写部分；"谁知道了什么"的信息差类单列 |
| 大纲兑现率 | 用于归因 | 按已确认大纲逐章核对：节拍覆盖、爽点兑现、钩子成立、没有提前写后面的剧情 |
| 机评成对胜率 | 编辑成对胜率的替身 | 评审模型成对比较，交换顺序各判一次；校准达标前只做初筛 |

## 5.3 有意不测

| 不测 | 原因 |
|---|---|
| 修辞、感官描写等文学性维度 | 对爽文没有区分力 |
| 字数达成率 | 编辑没批评过，保留为合格性检查，不作为指标 |

## 5.4 评测用检查器与生产校验分开

生产流程中的同步校验用事实日志做局部比对；评测用的一致性检查用全文读法，两者独立，避免自己审自己。两者共用同一套埋错校准，评测因此也能测出生产校验线的召回率。

# 六、校准

| 对象 | 方法 | 达标标准 |
|---|---|---|
| 送审门槛阈值 | 用第一轮已评稿子回测 | 与编辑批评基本吻合 |
| 第一批编辑反馈 | 把 16 条评语拆成问题清单，每个问题对应一个机评指标，在原稿上回测能否测出 | 第一批反馈即第一个校准集 |
| 一致性检查 | 在真实稿中人工埋 5～10 处矛盾，测召回和误报 | 召回率低时只用于相对比较 |
| 判断类机评 | 与编辑在同一批样本上做成对比较，计算一致率 | 以两位编辑之间的一致率为上限，接近上限才可用于迭代判断 |

注意事项：

- 样本量：20～30 组对比时，一致率的 95% 置信区间约为正负 17 个百分点，分不出 60% 和 90%。至少需要 80～100 组判断，可以由多位编辑 × 多组累积。
- 校准集必须包含类型跑偏的样本。评审模型和写作模型有相同的默认倾向，容易把"故作深沉"判为"写得好"。
- 评审模型尽量与写作模型不同；每次评测记录评审模型和提示词版本，换了就重新校准。

# 七、归因设计

成稿质量由两件事共同决定：方案（路线和大纲）和文笔（写作模型）。只看成稿无法区分是哪一层的问题。

| | 写作模型 A | 写作模型 B |
|---|---|---|
| 人工方案 | ① | ② |
| 系统方案 | ③ | ④ |

在 2～3 本书上跑四种组合，即可定位瓶颈：①② 好而 ③④ 差，问题在方案；①③ 好而 ②④ 差，问题在写作模型。之后每一轮迭代只改一个变量。

大纲兑现率与编辑判断结合，也能辅助归因：兑现率低，说明写作没执行好；兑现率高但不好看，说明方案本身有问题。

# 八、评测节奏

## 8.1 每周节奏

| 时间 | 做什么 |
|---|---|
| 周一 | 写下本周要回答的一两个问题，只改一个变量 |
| 周一至周二 | 在固定样本上生成，机评筛掉不达标的稿子 |
| 周三至周四 | 编辑成对比较，标原因 |
| 周五 | 统计结果，更新指标状态，定下周问题 |

## 8.2 里程碑

| 里程碑 | 内容 |
|---|---|
| M0 | 第一批反馈拆成问题清单，送审门槛阈值完成回测 |
| M1 | 2×2 归因实验完成，定位主要瓶颈 |
| M2 | 判断类机评与编辑一致率达标 |
| M3 | 全文评测达到阶段退出标准，进入线上小流量测试 |

全文评测每两三周做一次，作为里程碑检验。

# 九、待决问题

| 问题 | 为什么重要 | 谁来定 |
|---|---|---|
| 阶段退出标准是否合适 | 决定整套指标的松紧和何时上线 | 产品、编辑负责人 |
| 原因标签清单 | 编辑和机评之间的桥梁 | 编辑确认 |
| 编辑之间不一致时以谁为准 | 决定机评校准的靶子 | 产品，参考主编意见 |
| 方向、大纲、片段判断能否预测全文判断 | 决定分层评测是否成立 | 第一次全文评测时检验 |
| 节奏指标怎么定义 | 编辑评分最低的一项，目前没有好的量化方式 | 编辑标注原作爽点后归纳 |
| 评审模型用哪个 | 需与写作模型不同 | 确认公司内可用模型 |
| 线上测试看哪个指标 | 读者数据成为最终标准后的北极星 | 产品、平台 |

# 附：外部 benchmark 借鉴

没有现成 benchmark 能直接用。借鉴的是方法，而不是指标本身。

| 名称 | 借鉴什么 | 为什么不能直接用 |
|---|---|---|
| ConStory-Bench | 一致性错误分类；"前文怎么写、后文怎么矛盾"两段对照的输出格式；埋错校准；每万字矛盾数 | 英文为主，不是真正的续写，只测一致性 |
| WebNovelBench | 中文网文评分提示词；用真人文本做参照系 | 维度偏文学性，不测爽点、钩子、节奏 |
| SoloEnt 网文评测 | "按细纲执行好"不等于"好看"，两者分开测；编辑常见批评可转成检查项 | 单一题材，样本少 |
| EQ-Bench 创意写作 | 成对比较在高分段比细则打分更能拉开差距；AI 套话分的构造方法 | 英文，套话表需重建 |
| LitBench | 提醒校准的重要性：最强模型当评审，与人类偏好一致率约 73% | 英文短篇 |
| WritingBench | 每个任务生成专属检查清单，对应到我们就是用每版大纲做清单 | 不是小说专用 |
